# Конституция «Кот учёный»

Образовательная платформа. Здесь — договорённости, по которым пишется код.
Они обязательны и для людей, и для агентов. Общие правила перенесены из
конституции `vacation` и адаптированы к этому репозиторию.

## Стек

Next.js 16 (App Router, Cache Components, Partial Prefetching, Server Actions,
Turbopack), React 19 + React Compiler, TypeScript, Tailwind CSS 4,
shadcn/ui (стиль `base-maia` поверх Base UI), React Hook Form + Zod,
TanStack Query 5, Prisma 7 + PostgreSQL, better-auth (email + пароль).
Реальное время — отдельный Node-процесс на `ws` + Postgres `LISTEN/NOTIFY`.
Логи — pino.

## Конфиги

Прежде чем менять поведение инструмента, ищем его конфиг в корне
репозитория, а не настраиваем по месту.

| Файл                             | Что в нём                                                           |
| -------------------------------- | ------------------------------------------------------------------- |
| `next.config.ts`                 | `cacheComponents`, `partialPrefetching`, `reactCompiler`, Turbopack |
| `tsconfig.json`                  | strict, алиас `@/*` → `src/*`                                       |
| `eslint.config.mjs`              | правила Next, FSD, TanStack Query, совместимость с Prettier         |
| `.prettierrc`, `.prettierignore` | форматирование и исключения                                         |
| `prisma.config.ts`               | схема и миграции; адрес базы — из `DATABASE_URL`                    |
| `components.json`                | shadcn: стиль `base-maia`, пути для компонентов                     |
| `docker-compose.local.yml`       | Postgres и realtime для разработки                                  |
| `package.json`                   | доступные команды и зависимости                                     |

- Параметры локальной базы и окружения описаны в README. Не переносим сюда
  имена контейнеров, порты и секреты из других проектов.
- Новую переменную окружения сразу документируем в README в разделе запуска.
  Если появляется `.env.example`, поддерживаем его вместе с документацией,
  без реальных секретов.
- Для нового серверного кода используем единый модуль конфигурации
  `shared/config/server-env.ts`, вместо разрозненных `process.env`.
  Сейчас такого модуля нет; создаём его при первой задаче на конфигурацию.
  Серверные секреты не импортируем на клиент; публичные `NEXT_PUBLIC_*`
  значения отделяем от серверных.

## Архитектура — FSD

Слои сверху вниз: `app` → `widgets` → `features` → `entities` → `shared`.

- **Импорт только вниз.** Слайсы одного слоя друг друга не импортируют:
  фича не берёт из фичи, сущность — из сущности. Понадобилось двоим —
  значит, место в слое ниже, а собирает их слой выше (виджет или `app`).
- **Публичный API слайса** — `index.ts` (можно импортировать с клиента) и
  `server.ts` (только сервер: Prisma, `node:*`, секреты). Внутрь слайса
  снаружи не лезем. Серверные модули помечаем `import 'server-only'`.
- **Сегменты:** `ui/` — компоненты, `model/` — хуки, сторы, схемы, типы,
  `api/client/` — клиентские запросы, хуки запросов и мутаций,
  `api/server/` — серверный код и server actions, `lib/` — чистые функции.
- Правила, включая порядок импортов по слоям, проверяет
  `eslint-plugin-fsd-lint` для `src/`.
- `realtime/` — отдельный Node-процесс, а не слой FSD.

## Компонент — только UI

В компоненте — разметка, пропсы и вызовы хуков. Логика выносится в хуки:

- состояние, обработчики, производные значения, условия «можно ли
  отправить» — в `model/use-*.ts`;
- запросы и мутации — в `api/client/use-*.ts`.

Хук возвращает готовые данные и обработчики, компонент раскладывает их по
пропсам. Допустимо в компоненте только чисто визуальное состояние, которое
никуда не уходит (открыт ли попап).

**Один файл — один компонент.** Имя файла — имя компонента в kebab-case:
`MessageRow` → `message-row.tsx`. Вспомогательный подкомпонент, даже
маленький и нужный одному родителю, — отдельным файлом рядом в том же `ui/`,
а не второй функцией в файле родителя. Исключение — сгенерированные
shadcn-файлы в `shared/components/ui/`.

## UI — через shadcn

- Примитивы (кнопки, поля, диалоги, алерты…) — из shadcn:
  `npx shadcn@latest add <имя>`. Свой примитив не пишем, если есть готовый.
- Сгенерированные файлы в `shared/components/ui/` сохраняем в исходном
  виде, правим только форматирование. После каждого `add`/`apply` —
  `npm run format` с проверкой диффа на посторонние изменения.
  Составные компоненты поверх примитивов — в `shared/components/`.
- Пресет и цвета берём из текущих `components.json` и `globals.css`.
- Иконки — `lucide-react`.

## Формы — React Hook Form + Zod

- Схема — в `model/schema.ts` слайса. Одна и та же схема — в `zodResolver`
  формы и при проверке входных данных сервером: клиентскую валидацию
  обходят девтулзами.
- Сервер сначала проверяет сессию и доступ, затем делает `safeParse`,
  и только после этого выполняет операцию.
- Тексты ошибок — по-русски, в самой схеме.

## Тексты интерфейса

Спокойный деловой стиль. Текст не должен выглядеть сгенерированным нейросетью.

- Обращение на «вы», повелительное наклонение: «Выберите», «Укажите».
  Не «Кликните», не «Давайте».
- Одна мысль — одно предложение. Без склеек через «·» и тире между фразами.
- Подписи, подсказки и заголовки — без точки в конце, даже из двух
  предложений: точка только между ними.
- Без восклицаний, эмодзи, «Упс», «Готово!», вводных «пожалуйста» и
  оценочных слов («легко», «всего»).
- Термины — из предметной области платформы и одинаковые на всех экранах.
- Ошибка называет, что не так, без извинений, и подсказывает исправление,
  если оно известно.

## Данные и доступ

- Авторизация — better-auth. `proxy.ts` проверяет наличие cookie для
  оптимистичного редиректа; доступ к данным проверяется у самих данных.
- В каждом API-хендлере проверяем сессию через `getApiSession` из
  `shared/lib/api-guard.ts`. Серверные функции проверяют доступ к конкретному
  ресурсу; например, участие пользователя в беседе.
- Роль, идентификатор пользователя и права не принимаем на веру из
  клиентского запроса. Для операций с ограничением по роли явно перечисляем
  разрешённые роли на сервере. Роли `student`, `teacher`, `admin` уже есть
  в схеме, но сами по себе сейчас не ограничивают доступ.
- Чат использует route handlers и TanStack Query для чтения и мутаций.
  Этот контракт сохраняем; server actions используем для новых сценариев,
  когда они подходят. Для action результат —
  `{ ok: true, data } | { ok: false, error }`, ожидаемые ошибки не бросаем
  наружу. В API сохраняем принятые HTTP-статусы и формат ответа.
- Опрос (polling) — через route handlers в `app/api/`, не через server
  actions: Next выполняет экшены одного клиента по очереди.
- База — `shared/lib/prisma`. Схема — `prisma/schema.prisma`.
- Секреты, session cookies и токены не выводим в чат, логи и репозиторий.
  Локальные браузерные проверки выполняем в отдельном контексте с тестовой
  учётной записью через действующую авторизацию better-auth. Обходы
  авторизации в продукт не добавляем, проверки прав не отключаем.
  Временные сессии и файлы после проверки удаляем.

## Cache Components и Partial Prefetching

Включены `cacheComponents: true` и `partialPrefetching: true`.

- В компонентах страниц чтение `searchParams`, `cookies()`, `headers()`
  и сессии, а также незакешированные асинхронные данные — внутри
  `<Suspense>` с осмысленным fallback.
- Общие данные кешируем через `'use cache'` с явным `cacheLife`, исходя
  из допустимой свежести. Пользовательскую сессию не помещаем в общий кеш.
- Если библиотека использует случайные числа или текущее время до чтения
  runtime API, необходимость `await connection()` сверяем с установленной
  версией Next. Рецепты Auth.js сюда автоматически не переносим.
- Перед работой с кешем и prefetch читаем
  `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`
  и связанные гайды установленной версии Next.

## React Compiler

Включён `reactCompiler: true`.

- `useMemo`, `useCallback` и `memo` ради производительности не пишем —
  мемоизирует компилятор.
- Правила `react-hooks/*` в ESLint (purity, refs, set-state-in-effect…) —
  это диагностика компилятора, их не глушим.
- `npm run compiler:check` должен подтверждать совместимость компонентов.

## Проверки после фичи

Доступные сейчас команды запускаем от быстрых к медленным, останавливаясь
на первой ошибке:

```bash
npm run typecheck && npm run lint && npm run format:check && npm run compiler:check && npm run build
```

Единой команды `check`, тестового раннера, `test`, `test:int`, `test:browser`
и git-хуков в этом репозитории пока нет. Не считаем их настроенными и не
выдаём незапущенные проверки за пройденные. При добавлении тестов включаем
их в общий порядок перед `compiler:check` и сборкой. Если вводим хуки,
быстрые проверки выполняем перед коммитом, интеграционные, браузерные и
сборку — перед push. Хуки не заменяют полную проверку рабочей копии.

**Сложные фичи, которым нужна визуальная проверка или проверка взаимодействия,**
дополнительно проверяем через браузер на работающем приложении: многошаговые
формы, диалоги, сложные таблицы и связанные действия на нескольких экранах.
Проходим основной пользовательский сценарий, изменённые состояния, ошибки
и внешний вид. Агент сообщает, что проверил и какие проблемы нашёл. Если
проверка недоступна, явно сообщает причину и что осталось проверить.
Автоматические браузерные тесты эту проверку не заменяют.

Все необходимые проверки зелёные и проверка в браузере пройдена — фича готова.
Для документации и форматирования запускаем относящиеся к ним проверки.
Не запускаем сборку одновременно с `next dev` в одной `.next`.

## Тесты

- **TDD для изменений поведения:** сначала определяем публичные границы
  проверки, затем по одному срезу: один тест → падение именно из-за
  отсутствующего поведения (Red) → минимальный код → зелёный тест (Green).
  Ошибка окружения не считается Red. Следующий срез — после зелёного
  предыдущего; рефакторинг — после зелёных тестов с повторной проверкой.
  Тесты после реализации не называем TDD. Для документации, форматирования
  и других изменений без поведения цикл не нужен.
- **Как писать** — по локальному скиллу
  `.agents/skills/testing-best-practices/SKILL.md`: названия
  `Should <observable behavior>` по-английски, результат через публичный
  контракт, повторяющиеся случаи — `forEach`. Ожидаемое значение —
  конкретный пример из жизни, а не пересчёт тем же способом, что в коде.
- При настройке раннера используем **Vitest**. Тест рядом с исходником:
  `format-date.test.ts` возле `format-date.ts`; импорты
  `describe`/`it`/`expect` — явные. По умолчанию окружение node; для DOM —
  `// @vitest-environment jsdom` первой строкой.
- Время — через `vi.useFakeTimers()` + `vi.setSystemTime()` с восстановлением
  после теста; внешнее окружение — через подмену границы конфигурации.
- Интеграционные — `*.int.test.ts`, с настоящим Postgres и отдельной
  тестовой базой. Рабочую базу не очищаем. Подменяем внешние границы,
  а не проверяемую бизнес-логику.
- Браузерные — `*.browser.test.tsx`, Vitest + Playwright и
  `vitest-browser-react`, настоящие стили приложения. Подменяем серверную
  границу, UI и взаимодействия проверяем настоящие.

## Процесс

- **Сначала план, потом код.** На задачу «спроектировать» — план и развилки
  с вариантами; код — после одобрения.
- **Декомпозиция на малые шаги.** Задачу дробим на шаги с видимым результатом
  и зелёными проверками. Перед шагом — план: что увидим, какие файлы
  появятся или поменяются. Для ещё не согласованной реализации ждём «да»;
  уже разрешённую работу повторно не согласовываем.
- **После каждого шага — название коммита.** Агент предлагает его в стиле
  истории (`feat: добавить …`), коммитит человек сам.
- **Версия — один раз за релиз.** Перед предложением повышения сравниваем
  `package.json` с `origin/main`, если эта ветка доступна: `feat:` требует
  minor, `fix:` — patch; если поднят только patch, а добавилась фича,
  дотягиваем до minor. Уже поднятую minor повторно не увеличиваем.
  `test:`, `chore:`, `ci:`, `docs:` версию не меняют.
  Согласованное повышение — `npm version <minor|patch> --no-git-tag-version`,
  чтобы обновился и `package-lock.json`.
- Перед новой фичей ищем готовые решения и соглашения в текущем проекте.
  Заимствования из других репозиториев адаптируем осознанно.
- **README в каждом слайсе** (`entities/*`, `features/*`): назначение,
  причины решений, существенные отличия от использованного референса,
  раздел «Публичный API». Комментарии в коде — по-русски и про «почему»,
  а не «что».
- **Миграции:** `prisma/schema.prisma` →
  `npm run db:migrate -- --name <имя>` → `npm run db:generate` →
  перезапуск `next dev` (клиент Prisma кешируется в `globalThis`).
  Вручную SQL миграций не пишем. Для изменения таблиц better-auth сначала
  `npm run auth:generate`, затем проверяем дифф схемы; полный цикл —
  `npm run db:sync`.
